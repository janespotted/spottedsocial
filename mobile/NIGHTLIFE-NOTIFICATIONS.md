# Nightlife notification coverage

This add-on follows the complete notification repair (4bc9f37). Apply BOTH
notification migrations, in order. It is not yet deployed or active.

## Notification behavior

| Event | Recipients and limits | Destination |
|---|---|---|
| First Out tonight, including typed locations/private parties | All eligible audience members who opted in, including eligible mutuals; close friends processed first; no 20-person cap; once per sender/night | Map |
| First TBD tonight | Same audience and preferences; once per sender/night | Map |
| Confirmed change of bar | Defaults to people who marked sender a close friend; they must be Out/TBD and authorized by sender's audience; skip people already there; maximum 3 per sender/recipient/night, at least 30 minutes apart; don't repeat a venue | Map |
| Private-party invitation | Host explicitly selects a direct friend within their sharing audience | Party screen |
| Private-party invitation accepted | Host | Party screen |
| Party address requested | Host | Party screen |
| Party address approved | Requesting friend; generic push with no address | Party screen; authenticated address fetch |
| Friend request and acceptance | Named recipient; both are now generated by saved relationship changes | Activity |
| DMs, photos, shared posts | Thread recipients | Exact thread |
| Meet-up, venue invite, and acceptances | Named recipients | Activity |
| Plan invitation / I'm down | Named recipients / plan owner | Plans |
| Post comment, like, tag | Owner/tagged recipient, subject to privacy | Post |
| Daily/weekend prompts | Existing city-local schedule and opt-out rules; campaigns remain disabled until enabled | Check-in / Plans |
| Morning After | Device-local 10am recap in profile city | Private recap |

Out and TBD announcements are generic and contain no venue ID. Staying-in users
can receive these generic updates, but not automatic bar-location alerts. Direct
invitations are intentionally unaffected: someone can invite a friend who's home.
Notification preferences never expand the sender's sharing audience or defeat
blocks/hiding. First Out is not also sent as a bar-arrival alert.

## Native screens

- Settings → Friend activity alerts: all eligible friends/mutuals, close friends,
  or off; separate choices for first Out/TBD versus subsequent bar changes.
- Private-party check-in confirmation → Party invitations & address.
- A friend's private-party card → View party / request address.
- Activity → Private parties, with actionable View buttons.
- Host saves an address and approves/declines requests in the Party screen.
  Accepting an invitation does NOT grant address access. Address approval is a
  separate explicit host action. No private coordinates are added or widened.
- Blocks, leaving a party, nightly expiry or changing its address revoke access.
  Leaving a party deletes that party's request grants so reopening a new party
  cannot reuse old approvals. Repeated requests/invites are idempotent.

## Backend and privacy implementation

`20260922213920_nightlife_notification_coverage.sql` adds preferences, private-party
request RPCs, source-event dedupe and triggers for nightlife changes and initial
friend requests. The earlier queue and worker deliver these alerts with retries.
Native status saves persist the selected audience before committing status.
Old client nightlife notifier calls are suppressed to prevent duplicate alerts.

New types: friend_out, party_invite_accepted, party_address_approved. Existing
friend_planning, friend_arrived_venue, private_party_invite and address_request
are connected to source events or authorized party RPCs.

Deploy both SQL migrations before shipping the new app, then deploy the updated
send-push function plus the earlier worker/campaign functions. Keep JWT checks on.
Regenerate Supabase client types after migration. The package includes the small
notification metadata type change needed by this build.

No new activation is performed by this migration: it inherits the queue's global
delivery switch. If delivery is already enabled, applying this migration begins
creating the new notifications for FUTURE user actions. Do not apply to live
users until that release behavior is intended. It does not backfill past activity.

## Deliberately not added

No notification when someone goes home, no public private-party address alerts,
no alerts about strangers, no low-density crowd/FOMO broadcasts, no dormant Yap
notifications, and no extra promotional nudges. These do not help the current
app's core friend coordination flow. Existing meet-up, plan, venue-invite and
engagement features retain the earlier repair; this is not a new plans product.

The server can retry committed events. Actions that never reach the server still
require user retry; this does not implement an offline action queue. One native
APNs token per profile remains a limitation. Exact-once display cannot be
promised after provider/network failures.
